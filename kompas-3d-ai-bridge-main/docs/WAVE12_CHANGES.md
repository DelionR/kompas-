# Волна 12 — каталог оборудования и поиск по документам

**Поверхность:** 54 → 56 (`kompas_cabinet_catalog_search`, `kompas_docs_search`).
**Тесты:** 455 → 501 (46 новых, `tests/test_wave12.py`).

Волна закрывает два пробела, найденных сравнением с конкурентами
(`mcp_servers_comparison.md`): подбор изделий по параметрам, заявленный у
`sans-calc-mcp`, и поиск по документам со ссылкой на источник, реализованный у
`SwitchScope`.

## 1. `kompas_cabinet_catalog_search` — подбор оборудования

`src/cabinet_catalog.py`. Поиск по каталогу: автоматы, УЗО, контакторы,
клеммы, шины, блоки питания. Фильтры:

| Поле | Смысл |
|---|---|
| `kind` | тип изделия |
| `poles` | число полюсов (одно или список) |
| `rating_min_a` / `rating_max_a` | диапазон номинала |
| `trip_curve` | время-токовая кривая: B, C, D |
| `breaking_ka_min` | отключающая способность не ниже |
| `leakage_ma`, `rcd_type` | ток утечки и тип УЗО |
| `mount` | `din` / `panel` |
| `width_max_mm`, `height_max_mm`, `depth_max_mm` | ограничение по габариту |
| `manufacturer`, `series`, `text` | точное совпадение и подстрока |

### Зачем это связывает слои

Каждая найденная позиция возвращается с полем `layout` — готовой записью
библиотеки раскладки:

```json
{"lib_key": "brk-3p-c25", "name": "Автомат 3P, кривая C, 25 А",
 "width_mm": 52.5, "height_mm": 85.0, "rail_offset_mm": 45.0, "depth_mm": 68.0}
```

Её можно передать прямо в `kompas_cabinet_layout_build` — тест
`test_selected_item_feeds_layout_build` проверяет, что габарит доходит до
координат: `y + rail_offset = ось рейки`. Параметры позиции (номинал,
отключающая способность) — вход для `kompas_cabinet_calc`.

Так замыкается цепочка **подбор → габарит → раскладка → расчёт**, которой не
было: раскладка требовала габарит, а габарит брался из головы.

### Откуда данные

**Из модуля — ниоткуда.** Каталог приносит вызывающая сторона: полем `catalog`
или файлом в `catalog_path`. Чтение файлов допускается только внутри корня
проекта и текущего каталога; путь наружу отклоняется.

В репозитории лежит `data/cabinet_catalog.example.json` — **100 реальных
позиций IEK**, снятых с открытых карточек изделий на `www.iek.ru`
(2026-09-20): 79 автоматических выключателей KARAT ВА47-29 (1P–4P, кривые
B/C/D, 1–63 А, 4,5 кА), 19 УЗО ВД1-63 тип А (2P/4P, 10/30/100 мА), 1 контактор
ARMAT KMR. У каждой позиции — артикул, серия, ссылка на карточку и строка
источника.

#### Что показала проверка на реальных данных

Две вещи, из-за которых синтетическая заглушка была не просто неточной, а
вредной.

**1. Реальный модуль — 18 мм, а не 17,5.** У IEK ширина растёт как
18 / 36 / 54 / 72 мм на 1P–4P; это подтверждено дважды — габаритом индивидуальной
упаковки в карточке и числом модульных расстояний. УЗО ещё шире: 2P — 42 мм,
4P — 77 мм (шаг не кратен, поэтому брать «модуль × полюса» нельзя).

На плите 600 мм в ряд входит **26** однополюсных автоматов. Заглушка на 17,5 мм
обещала **27** — лишний слот, который в щит не влезет. Разница в полмиллиметра
на изделии даёт целый фантомный модуль на ряду. Тест
`test_row_capacity_with_real_width` фиксирует 26.

**2. Подбор по току КЗ отказывает там, где «на глаз» всё подходило.**
Трансформатор 630 кВА с uк 5,5 % даёт на вводе **17,4 кА**, а вся серия ВА47-29
имеет отключающую способность 4,5 кА — подбор возвращает `selected: null`.
Если учесть линию (40 м кабеля 4 мм²), ток падает до **1,17 кА**, и тогда
находится MVA20-3-040-C. Оба исхода зафиксированы тестами
`test_breaker_is_refused_when_fault_current_exceeds_capacity` и
`test_line_impedance_brings_fault_current_down`.

#### Что в примере осталось незаполненным и почему

- **`rail_offset_mm` — пусто.** Производитель не публикует смещение оси
  DIN-рейки; раскладка применит соглашение (центр по высоте). Заполнять его
  «примерно 45 мм» значило бы подменить отсутствующее правдоподобным.
- **Контактор ARMAT KMR — без габарита.** В карточке сказано «2 модуля», но
  габарит упаковки 50 мм, а не 36. Расхождение не разрешено, поэтому размер
  оставлен пустым и позиция уходит в `unverified` — тест
  `test_contactor_without_dimensions_is_not_placed`.

Файл по-прежнему помечен `"example": true`: это выборка двух серий, а не
каталог для проектирования — ряд мог измениться, а юридически для коммерческого
применения нужна выгрузка производителя (поле `legal` в файле).

Позиция без обязательного габарита не подставляет «среднее по рынку»: поле
`layout` остаётся пустым, причина пишется в `unverified_reason`, а с флагом
`need_geometry` позиция уходит в `unverified` и вердикт становится
`computed_with_gaps`.

## 2. `kompas_docs_search` — поиск по документам

`src/docs_search.py` + `src/docs_tools.py`. Полнотекстовый поиск по файлам
проекта. Каждое совпадение — это цитата с адресом:

```json
{"file": "docs\\WAVE11_CHANGES.md", "line": 35,
 "text": "## Ключевое решение: отказ вместо экстраполяции"}
```

Дисциплина та же, что у `SwitchScope`: отвечать можно только тем, что лежит в
файле, и отвечать с указанием, где именно. Отличие честно названо — поиск
**полнотекстовый, не семантический**: все слова запроса должны встретиться в
строке, поэтому неточная формулировка даёт пустой результат, а не
правдоподобный ответ. Векторной базы нет, интернет не используется.

Ограничения: чтение только внутри корня проекта и текущего каталога; предел
`max_files` (4000) сообщается через `truncated`, чтобы пустой результат при
усечении не читался как «в проекте такого нет»; бинарные файлы пропускаются.

## Что оператор заметит

- Оба инструмента только на чтение, КОМПАС не нужен: их можно использовать
  отдельно от моста.
- Ответ каталога содержит `provenance` с источником; если источник не указан,
  ответ об этом сообщает.
- Новые файлы: `src/cabinet_catalog.py`, `src/docs_search.py`,
  `src/docs_tools.py`, `data/cabinet_catalog.example.json`.

## Честные ограничения

- Пример каталога — **не** каталог изготовителя. Перед использованием в проекте
  его нужно заменить выгрузкой производителя; производитель и артикул остаются
  за пользователем.
- Поиск по документам даёт цитату, а не проверенную выдержку из действующей
  редакции нормы. Сверка с редакцией остаётся за инженером.
- Фильтр по производителю и серии работает только если эти поля заполнены в
  каталоге; в примере они пусты, поэтому фильтр по ним даёт пустой результат.

## Дефекты и ложные ожидания

Реальных дефектов в коде прогон не выявил. Три падения были на неверных
ожиданиях в тестах:

1. элемент раскладки не хранит `width_mm` — габарит лежит в библиотеке, а
   элемент хранит координаты. Тест теперь проверяет главное: `y +
   rail_offset = ось рейки`, то есть габарит из каталога действительно дошёл до
   расстановки;
2. контекст вокруг строки на краю файла короче трёх строк — совпадение перенесено
   в середину файла;
3. `build_layout` возвращает библиотеку списком, а не словарём.

## Пример вызова

```json
{"kind": "breaker", "poles": 3, "trip_curve": "C",
 "rating_min_a": 25, "breaking_ka_min": 6, "limit": 4}
```

Ответ: четыре позиции 25–50 А, ширина 52.5 мм, `example: true`,
`provenance.source` — «Типовые модульные габариты по DIN 43880. Не каталог
изготовителя.»
