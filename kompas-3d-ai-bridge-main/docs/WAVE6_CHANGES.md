# Волна 6: сухой прогон (dry run) мутирующих инструментов

Поверхность инструментов: **46 → 47**.

Патч `wave6.patch` накладывается поверх `wave1` … `wave5`.

## Зачем

До этой волны у моста был ровно один инструмент с сухим прогоном —
`kompas_export` с `apply=false`. Все остальные мутирующие операции агент
вызывал вслепую: опечатка в аргументе, файл не в рабочем каталоге, запись в
защищённый корень, незащищённая версия КОМПАСа — всё это обнаруживалось уже
после того, как вызов ушёл в COM, а иногда и после того, как файл был
перезаписан.

Добавлять параметр `dry_run` в схему каждого из двух десятков инструментов
значило бы расплодить двадцать разных реализаций «почти того же». Вместо
этого сделан один инструмент-предпросмотр, который знает о каждом мутирующем
действии из явного манифеста.

## Что добавлено

**`kompas_dry_run`** (`dryrun.plan`) — один инструмент на все мутирующие
вызовы:

```json
{"tool": "kompas_material_set",
 "arguments": {"filename": "part_AGENT_COPY.m3d", "material_name": "Steel",
               "density": 7.85, "evidence_source_relative_path": "src_AGENT_COPY.m3d"},
 "version": "25.0.0.1234"}
```

Ответ содержит:

- `verdict` — `blocked` / `ready_with_unknowns` / `ready`;
- `blocking_checks`, `unknown_checks` — имена проверок, а не «что-то не так»;
- `checks` — каждая проверка со статусом `pass` / `fail` / `unknown` / `note`
  и пояснением;
- `argument_problems` — конкретные нарушения схемы с путём до поля;
- `target`, `work_directory`, `version_guard`;
- `unverifiable` — то, что без Automation узнать нельзя;
- `limits` — прямое напоминание, что сухой прогон не доказывает успех.

## Что именно проверяется

| Проверка | Что даёт |
|---|---|
| `tool_known` | инструмент существует |
| `mutating` | есть ли смысл в сухом прогоне (для read-only — `note`) |
| `arguments` | схема аргументов целиком: типы, enum, границы, лишние поля |
| `target_path` | путь относительный и не выходит из рабочего каталога |
| `target_exists` / `target_absent` | файл есть (для изменения) или его нет (для создания) |
| `target_suffix` | расширение соответствует действию |
| `agent_copy` | в имени есть `_AGENT_COPY` там, где это требуется |
| `write_root` | путь внутри разрешённых корней записи |
| `not_protected` | путь не внутри защищённого корня |
| `job_allowlist` | задание перечислено в `jobs/allowlist.json` |
| `version_guard` | действие не запрещено матрицей версий |

Валидатор схемы — минимальная реализация подмножества JSON Schema, которое
реально используется каталогом: `type`, `enum`, `oneOf`, минимумы и максимумы,
длины строк, `minItems`/`maxItems`, вложенные `properties`,
`additionalProperties`, `minProperties`/`maxProperties`. Внешних зависимостей
нет.

## Ключевые решения

**Манифест вместо разбросанных проверок.** `ACTION_PREFLIGHT` в `src/dryrun.py`
явно описывает каждое мутирующее действие: какой параметр держит путь, какое
расширение ожидается, нужен ли `_AGENT_COPY`, что действие делает (`create` /
`modify` / `export` / `restore` / `script` / `view` / `ui` / `document` /
`none`). Тест `test_every_mutating_action_has_a_manifest_entry` требует запись
для каждого мутирующего инструмента каталога — иначе сухой прогон молча
проверит только схему аргументов и отрапортует «готово». Обратный тест ловит
устаревшие записи.

**Неизвестное названо неизвестным.** Если действие работает с активным
документом (`stamp.write`), путь из аргументов узнать нельзя, и проверка
получает статус `unknown`, а не `pass`. Итог тогда
`ready_with_unknowns` — агент видит, чего он не знает.

**Без версии — «неизвестно», а не «заблокировано».** Для действия из
`guarded_actions` сухой прогон без переданной версии отвечает `unknown`:
поднимать `fail` значило бы утверждать, что мост знает версию running-КОМПАСа.
Версия читается только когда действие действительно защищено — так же, как в
воркере.

**Сухой прогон ничего не делает.** В ответе всегда `would_execute: false`. Тест
сверяет байтовый хэш целевого файла и список файлов рабочего каталога до и
после: ни записи, ни новых файлов.

**Всё, что требует COM, уходит в `unverifiable`.** Сухой прогон не обещает, что
интерфейс существует, что геометрия получится или что чтение после перезаписи
подтвердит изменение. В `limits` прямо сказано: прогон доказывает, что ничего
обнаружимого не мешает, а не то, что вызов удастся.

```bash
python -m unittest discover -s tests -p "test_wave6.py" -v
python tests/test_mcp_stdio.py          # PASS test_mcp_stdio 47
```

## Что намеренно не сделано

1. Добавление `dry_run` в схему каждого мутирующего инструмента — один
   предпросмотр покрывает их все и не расходится по реализациям.
2. Проверки, требующие КОМПАС: существование интерфейса, состав сборки,
   достижимость селектора. Они в `unverifiable`.
3. Откат по результату сухого прогона: он и так ничего не меняет.
4. Подтверждение на живом КОМПАСе — стенда не было.
