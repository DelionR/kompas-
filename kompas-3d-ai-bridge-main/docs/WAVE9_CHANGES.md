# Волна 9 — материализация раскладки

Волна 8 считала **координаты**. Волна 9 превращает их в **последовательность
вызовов моста** и умеет эту последовательность исполнить.

Поверхность инструментов: **50 → 52**.

## Что добавлено

| Файл | Назначение |
|---|---|
| `src/cabinet_materialize.py` | план материализации — чистые функции, без COM |
| `src/cabinet_exec.py` | исполнитель плана, COM подтягивается лениво |
| `src/cabinet_tools.py` | адаптеры к реестру действий |
| `src/dryrun.py` | запись `cabinet.materialize_apply` в манифест предпросмотра |
| `tests/test_wave9.py` | 50 тестов |
| `docs/STEP_IMPORT_PIPELINE.md` | план конвейера «STEP → .m3d» (запланировано) |

### Инструменты

- **`kompas_cabinet_materialize_plan`** — чистый расчёт, `readOnlyHint: true`.
- **`kompas_cabinet_materialize_apply`** — исполнение, требует явный
  `apply: true`. Без флага возвращает план и ничего не делает.

## Ключевые решения

### План ссылается на экземпляры символически

Числовой индекс компонента в дереве сборки известен только КОМПАСу, после
вставки. Поэтому в плане селектор выглядит как
`{"from_step": 6, "field": "component_index"}`, а исполнитель подставляет число
из ответа предыдущего шага. Угадывать индекс нельзя: обращение к не тому
экземпляру молча испортит сборку.

### Сеты режутся под ограничение паттерна

`kompas_component_pattern_linear` принимает `count` от 2 до 20. Сет из 24 клемм
одним вызовом не собрать, поэтому он режется на равные части — `[12, 12]`.
Каждая часть: вставка, позиционирование, паттерн. Смещение части считается по
шагу сета (`ширина детали + внутренний зазор`).

Второй и последующие подсеты вставляются с `allow_duplicate = true`: мост по
умолчанию отказывает в повторной вставке того же файла.

### Тело создаётся один раз на ключ библиотеки

Двенадцать клемм — один файл `term_AGENT_COPY.m3d` и один паттерн, а не
двенадцать деталей и двенадцать вставок. И только для **используемых** позиций:
библиотека может содержать сотни записей, а в щите стоять пять.

### Два вида источника геометрии

- **`primitive`** — габаритный блок через `kompas_part_create` +
  `kompas_part_add_primitive` (kind=`block`). Работает без библиотеки
  оборудования: тело строится по подтверждённому размеру из библиотеки щита.
- **`fragment`** — готовый `.m3d` по полю `fragment_ref`.

План от вида источника не зависит. Появится библиотека фрагментов — заменится
только источник тела. Реализовано сейчас, потому что это дешёво: разница в две
строки, а переделка плана потом стоила бы дорого.

### Часть шагов не автоматизируется

Чекпоинт, перечень компонентов, габарит и снимок видового экрана имеют **другой
контракт** — не `session`, а `bridge_root` или `root`. Они остаются в плане с
`automated: false` и попадают в `deferred`. Притворяться, будто исполнитель их
вызвал, нельзя.

### Маркируется только исходный экземпляр сета

Позиционные обозначения на двадцати четырёх клеммах потребовали бы двадцать
четыре вызова с числовыми индексами, которых нет. Маркируется первый экземпляр,
остальные наследуют обозначение через паттерн. Ограничение зафиксировано в
`limits`.

## Дефекты, пойманные тестами и живым прогоном

### Ссылки шагов указывали не туда

Первая версия брала «предыдущий шаг» как `seq - 1`. Между вставкой и
позиционированием это давало **создание тела**, а не вставку: трансформ
обращался бы к детали, а не к экземпляру. Поймано живым прогоном с проверкой
«каждая ссылка ведёт на `assembly.insert_component`». Теперь номер вставки
сохраняется в переменную, а не вычисляется отставанием.

### Исполнитель вызывал шаг с `selector=None`

Если `component_index` вернул `None` (нет `readback.component_count`),
подстановка возвращала `None`, и шаг выполнялся с пустым селектором. Теперь
`None` означает «индекс неизвестен» и шаг уходит в `skipped`.

### Шаги вставки строились без имени сборки

План создавал `insert` с пустым `assembly_filename` — вызов, гарантированно
обречённый. Теперь без сборки размещение не планируется вовсе; тела при этом
создаются, потому что от сборки не зависят.

### Тела создавались на всю библиотеку

Библиотека щита — это справочник, а не состав. Создавать файл на каждую из
сотен записей бессмысленно. Теперь тела строятся по используемым ключам.

### Два ожидания в тестах были неверны

`no_assembly` ожидал «шагов нет вообще» — неверно, тела создаются.
`non_critical_failure` ожидал одну ошибку маркировки, а позиций две.

## Что осталось за кадром

- **Нумерация экземпляров подтверждена только чтением кода.** Что
  `component_count - 1` — это индекс последнего вставленного, нужно проверить на
  живом КОМПАСе. Отмечено в `limits`.
- **Габаритный блок — не модель изделия.** Это занимаемый объём по
  подтверждённому размеру. Настоящая геометрия требует конвейера импорта — см.
  `docs/STEP_IMPORT_PIPELINE.md`.
